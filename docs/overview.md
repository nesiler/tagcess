# tagcess: overview

Status: draft. This file is the single reference summary of the project.
Detailed design builds on it. If something conflicts, update this file first.

Labels: **[Decided]** developer decision, **[Proposed]** proposal (awaiting confirmation), **[Open]** open issue.

## 1. Goal
Managing the access layer of a company VPN usually means hand-editing several config files plus a Zitadel screen.
tagcess brings these tasks into one UI. It acts as a bridge between Caddy, Headscale and Zitadel.

Goals:
1. Which roles can open each internal site is managed from the UI: adding a site, changing roles, removing a site. **[Decided]**
2. Zitadel role assignments are carried into Headscale groups automatically and, where possible, immediately. **[Decided]**
3. Every setting that can be managed is managed from the UI; no manual steps are left behind. **[Decided]**

Core principle: **user and role management lives only in Zitadel.** tagcess reads role assignments and keeps no second user store. **[Decided]**

## 2. Scope
| In scope | Out of scope |
|---|---|
| Internal sites and access rules in Caddy | WireGuard, wireguard-ui, dnsmasq (a legacy path that is switched off after migration) **[Decided]** |
| Headscale: policy (groups, ACL, tags), devices, keys, DNS records | Creating users and assigning roles in Zitadel (stays in the Zitadel console) **[Decided]** |
| Zitadel → Headscale group sync | Problems of the applications behind the sites **[Decided]** |
| Redirect URIs of the oauth2-proxy app in Zitadel **[Decided]**; post-logout URIs are not written **[Decided]** | Writing to k8s (read-only) **[Proposed]** |
| k8s Ingress awareness and target health checks **[Decided]** | Public sites (served outside the VPN) |
| | Replacing Headplane or claiming parity with it: Headplane is ignored **[Decided]** |
| | Headscale features outside the device/key/policy/DNS set below: manual device registration, browser SSH, OIDC domain/e-mail filter management, deleting or renaming Headscale users, creating API keys **[Decided]** |

## 3. Users and access
- Only devops users use tagcess. **[Decided]**
- The UI is reachable only from the VPN; it sits behind Caddy + oauth2-proxy and requires the `devops` role. **[Decided]**
- The identity is taken from the oauth2-proxy headers (`X-Auth-Request-*`) and written to the audit record. **[Proposed]**

## 4. Components
| Component | Version | Notes |
|---|---|---|
| Headscale | v0.29.4 | systemd, SQLite; policy in `database` mode, DNS extra records file |
| Caddy | v2.8.4 | `Caddyfile` generated by tagcess; admin API used for `/adapt` and `/load` |
| oauth2-proxy | v7.15.4 | `allowed_groups` comes from the per-site parameter in Caddy |
| Zitadel | v4.16.0 | Roles live in a `vpn` project: devops, developer, standard. An Action writes these roles into the `groups` claim |
| Certificates | certbot | Wildcard per domain. Target: Caddy DNS-01 (a separate production step) **[Decided]** |

Site kinds handled by the model:
- Role-checked sites.
- Role-checked sites where API requests are exempt from the check.
- Unchecked sites, intentional.
- Unchecked sites, transitional.
- Locked system sites: the Zitadel gate, Headscale, wireguard-ui and tagcess itself.

### Import of an existing installation
Requirements that exist only for adopting an existing installation are labelled as such throughout the docs.
- Requests coming from WireGuard pass unchecked for now. In an existing Caddyfile, tailnet and explicitly allowed sources
  may pass while every other source gets 403. tagcess has no such source restriction: after adoption S-06 starts
  open, and after the first import the internal sites are also reachable from the internet; the developer accepted this.
  When WireGuard is switched off, S-06 is closed from the UI and only the tailnet remains. **[Decided]**

## 5. Functions
Numbers are used as references in requirements and tests.

### 5.1 Sites (S)
- **S-01** Site list: name, kind, roles, target, health status, last change.
- **S-02** Add, edit and delete a site. Fields:
  - Name(s): one site can have several hosts.
  - Kind: role-checked / no role (intentional) / no role (transition) / system site (locked template: zitadel, headscale, wireguard_ui, tagcess). **[Decided]** (ADR 0010)
  - Allowed roles: chosen from the roles in the Zitadel `vpn` project.
  - Target: the default is the k8s internal gateway; a custom address can also be given.
  - API exemption rules: header presence only (ready-made patterns Authorization, X-Api-Key, PRIVATE-TOKEN) and path regex; no free-form expressions **[Decided]** (ADR 0011).
  - Redirects and extra headers.
  - Maintenance mode, note, owner. **[Proposed]**
- **S-03** Generation from a single record: Caddyfile block, MagicDNS record, Zitadel redirect URI. The post-logout URI is not written. **[Decided]** (ADR 0012, ADR 0013)
- **S-04** Apply flow: generate → admin API `/adapt` → `/load` → write the file if it succeeded. If `/load` fails, the running config and the file stay unchanged. **[Decided]** (ADR 0005)
- **S-05** Locked system sites: `auth` (zitadel), `hs` (headscale), `vpn` (wireguard_ui) and tagcess itself are generated from a template and cannot be deleted; only limited fields are editable. `zitadel` and `tagcess` cannot be disabled, and tagcess's own role check cannot be broken. The purpose is to prevent locking yourself out through the UI. **[Decided]** (ADR 0010)
- **S-06** The single global switch that turns off the WireGuard free pass. When off, role-checked and role-less (`open`) sites return 403 to sources outside the tailnet; the `@api` exemption stays valid from every source. **[Decided]**
- **S-07** Certificates: until DNS-01 is in place, adding a new domain raises a warning. After the switch, certificates are left to Caddy. DNS-01 is a separate production step; site management does not wait for it. **[Decided]**

### 5.2 Sync (Y)
- **Y-01** Receives the Zitadel Actions v2 webhook and verifies its signature.
  - Events: `user.grant.*`, `user.deactivated`, `user.locked`, `user.removed`.
- **Y-02** Periodic full comparison (5 min): corrects things if a webhook is missed. **[Proposed]** (also the developer's fallback plan)
- **Y-03** Writes the role assignments in the Zitadel `vpn` project into the Headscale policy as `group:<role>`.
- **Y-04** If a person loses all their roles in the `vpn` project, or their account is deactivated, locked or deleted, their devices are expired (not deleted). On a role change only the group is updated. **[Decided]**
- **Y-05** Diff report: shows the difference between Zitadel and Headscale and the last sync result.
- **Y-06** Dry-run mode: the difference is computed but not applied. The first production run is made in this mode. **[Proposed]**

### 5.3 Headscale (H)
Detailed EARS items are in [requirements.md](requirements.md). All of the following are **[Decided]**.
- **H-01** Devices: listing (simple periodic refresh), rename, expire, delete, tag assignment, route and exit node approval; changing the expiry period and turning it on/off. For personal devices Y-04 takes precedence: a device expired on role loss is not re-enabled automatically when the role returns; it is re-enabled only with administrator approval (with a fresh eligibility read). Nodes carrying server tags (a list in settings) cannot be deleted, expired or have their tag changed. **[Decided]**
- **H-02** Users (Headscale side): listing and matching with Zitadel. No creation; users are created through OIDC login. No deletion or renaming. **[Decided]**
- **H-03** Pre-auth key and API key management. Personal pre-auth: only for an existing OIDC user, an active account and an allowed role; single use, default 1 hour, no upper limit on the lifetime (server keys are also produced this way and the lifetime is always explicit); on role loss an unused key is revoked at the next reconcile (≤5 min). Tagged pre-auth for shared devices. API key: list, expire and delete only; no creation. **[Decided]**
- **H-04** ACL editor: form view and raw HuJSON view (a plain textarea first); lossless document, role groups locked, empty documents and documents without `acls`+`grants` are blocked, locked mandatory tests, no writes while Zitadel is unreadable; validation before saving. **[Decided]** (ADR 0020)
- **H-05** Tag management (tagOwners) and shared devices. Shared devices are represented as tagged devices; the tag owner is `group:devops`. **[Decided]** The personal → tagged conversion is irreversible; it needs an extra confirmation and the warning "tagged devices are not expired on role loss (Y-04 bypass)". **[Decided]**
- **H-06** DNS: MagicDNS extra records. Records generated from sites are read-only; non-site records are added and edited by hand (`site.manual_dns` in `settings`). **[Decided]**
- **H-07** Headscale config: a secret-free summary from the host helper (current `allowed_groups`, last operation status) is displayed; the raw `config.yaml` is not exposed in the UI **[Decided]**. Changes need a restart, so they go through a separate confirmed flow. **[Proposed]**
  - The VPN entry condition (`oidc.allowed_groups` = devops, developer, standard) is managed here. **[Decided]**
  - Implemented with the host helper (ADR 0021). Only `allowed_groups` is edited at first; DNS fields come later. Before `allowed_groups` is enabled, it is verified in a lab with a real OIDC login that Headscale receives the `groups` claim. **[Decided]** The details a–f of ADR 0021 were accepted; they cover only `allowed_groups`. **[Decided]**

### 5.4 k8s (K), read-only
- **K-01** Finds internal Ingresses that are not in Caddy and offers an "add?" suggestion. **[Decided]**
- **K-02** Target health check. **[Decided]**
- **K-03** Two-gate audit: shows Ingresses that landed on the wrong entrypoint. **[Proposed]**

Design: ADR 0030, ADR 0031, ADR 0032. The ADRs as a whole are **Proposed**; the individual developer decisions are the boundaries below.
- **[Decided 2026-09-29]** An incomplete discovery suggestion can be stored and completed in the UI; storing is not opening access. For private
  sites, either all VPN users (`open/intentional`) or selected roles (`role`) are chosen explicitly; system locks are preserved.
- **[Decided 2026-10-04]** The first release supports a single Traefik profile and reads standard Ingress + Service objects; nginx is not supported.
  Gateway/CRD paths are shown as not scanned. Every real route conflict requires UI review; if the effective controller
  cannot be proven the result is uncertain and existing access is kept.
- **[Decided 2026-10-04]** On first connection the UI presents a read-only ServiceAccount/RBAC manifest and an authorised cluster administrator
  establishes the first trust; endpoint/CA/time-limited token are uploaded from the UI, expiry warnings and manual token replacement are done from the UI.
  An automatic renewal provider is not an exit condition of the first release; tagcess does not create k8s identities, RBAC or tokens.
- **[Proposed]** Full, paged snapshot; on an incomplete read, last good state + freshness; a separate persistent draft and only confirmed S-04
  transfer; separate target/Caddy health and presented-TLS measurement. In the two-gate audit, configuration risk, network observation and observation time are separate.
  There is no internet-side measurement component **[Decided]**; with no external evidence, "Internet reachability not tested" is shown.

### 5.5 Dashboard and alerts (P)
Alerts are shown only on the dashboard; there is no e-mail or chat notification. **[Decided]**
- **P-01** Dashboard **[Proposed]**: connected devices, last seen time, a "who can reach which site" matrix.
- **P-02** Alerts:
  - Sync error
  - Certificate expiry
  - Target down
  - Manual change (drift)

**[Decided 2026-09-29]** Initially target checks run every 60 s, inventory every 5 min, certificate expiry every 6 hours; a health alarm
opens after 3 consecutive failures and resolves after 2 successes; certificate thresholds of 30/14/7 days are info/warning/critical. All are changeable from the UI.
**[Proposed]** Alarm de-duplication, read/resolved distinction, maintenance and source freshness; losing a source is not a resolution. The dashboard role
matrix is the expected Caddy role access, not a guarantee of effective end-to-end access; detailed EARS criteria are in requirements K/P.

### 5.6 Import of an existing installation (G) **[Proposed]**
- **G-01** Import of the current Caddyfile, DNS records and policy. The Caddyfile is imported with a one-time seed file; the generated file must equal the existing one by `caddy adapt` JSON **[Decided]** (ADR 0010).
- **G-02** Moving the policy from file mode to database mode.
- **G-03** Converting e-mail based groups to provider identifiers.
- ~~**G-04** Removing Headplane.~~ Out of scope: Headplane is ignored. **[Decided]**

### 5.7 Audit (A)
- **A-01** Every change is recorded: who, when, what changed (diff). **[Decided]**
- **A-02** Every generated artifact (Caddyfile, policy, MagicDNS and other generated files) is committed automatically to a local git
  repository; the history carries who, when and which file, and contains no secrets. A commit is made only for the final artifacts
  that were applied and verified by read-back/hash, after the application; on a git failure the verified live state is kept and the commit is
  held as a durable, ordered retry intent. **[Decided]** (ADR 0016)
- **A-03** The UI can return to an earlier site version; a return is not a blind load but a new, audited change that goes through the same
  validate-confirm flow. The preview is read-only (validation + `/adapt` + diff); after confirmation the existing site change pipeline runs and the durable
  site source records + linked artifacts are updated in a single Change, so the next render does not undo the return. Rollback covers only the site source snapshot and
  the Caddyfile/MagicDNS/owned Zitadel URI artifacts; policy rollback is a separate item. **[Decided]** (ADR 0017)

## 6. Criteria

### 6.1 Technical decisions
| Topic | Decision |
|---|---|
| Language | Go, single binary **[Decided]** |
| UI | templ + htmx + own `internal/web/ui` components, embedded (Bootstrap was removed **[Decided]**, [rules](ui-guide.md)); CodeMirror 6 for the ACL editor **[Decided]** (ADR 0007); a plain textarea first, CodeMirror later **[Decided]** |
| State | SQLite: `modernc.org/sqlite`, our own small migrator, sqlc **[Decided]** (ADR 0006) |
| Runtime location | The VPN host; Docker, host network, `127.0.0.1` only **[Decided]** (ADR 0004) |
| Headscale policy mode | `database`: the policy is written through the API. The developer approved (§9.1) **[Decided]** |
| Config file | YAML, strict parsing, commented example **[Decided]** |
| Licence | Open source and free dependencies **[Decided]** (AGPL-3.0 with a commercial option, see [product-decisions.md](product-decisions.md)) |

### 6.2 Non-functional criteria **[Proposed]**
- **Not in the data path:** if tagcess crashes, the VPN and the sites keep working. Only management and sync stop.
  - Caddy asks oauth2-proxy directly, not tagcess.
- **Safe default:** access is not opened in case of doubt.
  - If Zitadel cannot be read, groups are not emptied; the last known state is kept.
- **Idempotent:** the same input always produces the same output. Running again is harmless.
- **Validate before applying:** for Caddy the admin API `/adapt` + `/load` (if loading fails, the running config and the file stay unchanged), for Headscale `CheckPolicy`. If a multi-step change is interrupted midway, the applied steps are rolled back.
- **Least privilege:**
  - The Zitadel service user can only read the `vpn` project and update the URIs of the oauth2-proxy app.
  - A read-only ServiceAccount is used on the k8s side.
- **Secrets:** not written to the repo or docs; read from a file or an environment variable.
- **Scale:** 15-30 users and about 25 sites. Performance is secondary, correctness primary.

### 6.3 Testing
- Development and tests run on local Docker Compose: Headscale, Caddy, oauth2-proxy, kind. **[Decided]**
- Zitadel and Postgres run only in a lab (a small k3s cluster); the local compose has no Zitadel and uses the lab Zitadel as the Headscale OIDC issuer (ADR 0014). **[Decided]**
- Rollout against a live installation:
  1. Dry run first.
  2. Then sync is enabled.
- Against live servers only reading is done; changes are made only when the operator explicitly asks. **[Decided]**

## 7. Architecture (high level)
```
Devops ──VPN──▶ Caddy ──forward_auth──▶ oauth2-proxy ──▶ Zitadel
                  │ (devops role)
                  ▼
               tagcess ──────────────▶ Headscale API (policy, device, key, DNS)
               │  ▲   ├─ writes Caddyfile + caddy reload (admin API)
               │  │   ├─ Zitadel API (reads roles, writes URIs)
               │  │   └─ k8s API (read-only)
               │  └── Zitadel Actions v2 webhook (over Tailscale)
               └── SQLite (sites, audit) + local git (generated files)
```

Open:
1. ~~Headscale restart~~: **Closed.** A systemd `.path` helper runs on the host (ADR 0008) **[Decided]**.
2. **Pod → tailnet access:** The tailnet path works: `tailscale ping` from the cluster node answers in 3 ms. Plain ping and TCP are blocked. The cause is policy: there is no `tag:k8s → tag:vpn-server` rule. An ACL rule for the webhook port is to be added; a real request from a pod will then be tried end to end. **[Open]** (low risk)
3. ~~Role of the Zitadel service user~~: **Closed.** `PROJECT_OWNER` only in the `vpn` project **[Decided]**. Authentication uses a JWT profile key (ADR 0009).
4. ~~How the provider identifier is written in the policy~~: **Closed.** Tried in compose; the `<provider identifier>@` form is accepted and resolves to the correct user **[Decided]** (ADR 0002). Safe method for the policy DB migration: [policy-database-migration.md](policy-database-migration.md).
5. **App URI write permission:** an initial write test was made with a temporary account holding `PROJECT_OWNER_GLOBAL`. With the permanent role in ADR 0009 (member of the `vpn` project, `PROJECT_OWNER`), `GetApplication`/`UpdateApplication` were **verified on a lab Zitadel**: the permanent role reads and writes; an unauthorised identity cannot write and the error is reported by type. Remaining: the operator removes the temporary test account and its permission. **[Open]**
6. **Closed [Decided]:** Installation-specific service names are not an exception in the product design.
   For every managed site, route matching and the target response are separate observations; if there is no match, the record/access/roles are kept
